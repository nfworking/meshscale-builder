# MeshScale Builder

Internal Rust build service/CLI used by MeshScale to turn a Git repository into a relocatable deployment output.

This is **not** the customer-facing MeshScale CLI.

## Current implementation

The implemented pipeline currently covers phases A-E (building, local execution and R2 upload):

1. Clone the requested GitHub repository.
2. Check out the exact requested commit.
3. Resolve the optional project directory.
4. Detect Next.js.
5. Detect npm, pnpm or Yarn.
6. Install dependencies using the project's normal package manager.
7. Run the project's normal Next.js build.
8. Read Next.js output-file-tracing manifests, excluding Next's generated `.next/standalone` tree.
9. Consume the `.nft.json` runtime traces generated by Next.js during the production build.
10. Produce .meshscale/output with manifest.json, static/, and runtime/.
11. Validate that the output contains no symbolic links or Windows junction/reparse-point links.
12. Upload the artifact to an immutable R2 prefix (unless `--no-upload` is set).

The builder does **not** modify next.config.* and does **not** force output: "standalone".

## Output layout

~~~text
.meshscale/
└── output/
    ├── manifest.json
    ├── static/
    │   ├── _next/
    │   │   └── static/
    │   └── ...
    └── runtime/
        ├── .next/
        ├── node_modules/
        ├── package.json
        └── .meshscale-server.cjs
~~~

New artifacts contain a production-only Node entrypoint:

~~~text
cd .meshscale/output/runtime
node .meshscale-server.cjs
~~~

It starts Next.js using the configuration captured in `.next/required-server-files.json`, rather than re-evaluating the source `next.config.*`. The builder neither edits the source configuration nor requires `output: "standalone"`.

The local runner and future edge runtime consume the manifest rather than depending on the original source checkout.

## Commands

Build:

~~~bash
cargo run -- build \
  --git-username nfworking \
  --git-repo example \
  --git-hash 0123456789abcdef0123456789abcdef01234567 \
  --git-branch main \
  --access-token "$GITHUB_TOKEN" \
  --build-id build_123 \
  --org-id org_123 \
  --project-id project_456
~~~

Monorepo application:

~~~bash
cargo run -- build \
  --dir apps/web \
  --git-username nfworking \
  --git-repo example \
  --git-hash 0123456789abcdef0123456789abcdef01234567 \
  --git-branch main \
  --access-token "$GITHUB_TOKEN" \
  --build-id build_123 \
  --org-id org_123 \
  --project-id project_456
~~~

The output defaults to .meshscale/output and can be changed with --output.

Build uploads by default and requires organization/project IDs and R2 configuration. It checks those settings before cloning/installing. For credential-free local build/run testing, append `--no-upload`; organization/project IDs are optional in that mode (but must be supplied together). Build records supplied IDs in `manifest.json`.

Build success JSON includes an `upload` object with bucket, prefix, uploaded file count and artifact bytes (`null` when upload is disabled). If upload fails after a successful build, the command fails but preserves the local artifact and reports its output path. `build_time_ms` includes upload time when enabled. Logs and upload progress go to stderr; result JSON goes to stdout.

## Local runner (phase D)

Run a built artifact:

~~~text
meshscale-builder run .meshscale/output
~~~

From the source checkout, use `cargo run -- run .meshscale/output`.

The runner validates the version-1 Next.js/Node manifest, required paths and link-free artifact before starting anything. Node must be on PATH and compatible with the Next.js version and native dependencies used by the build. Only run trusted artifacts: their Node code executes with your user privileges.

The Rust HTTP router listens at `http://localhost:3000` (IPv4 loopback). It spawns the manifest's entrypoint with its working directory and arguments, running the Next.js production server on `127.0.0.1:3100`. It waits up to 30 seconds for Node to listen; occupied ports, invalid manifests, startup failures and unexpected Node exits fail explicitly. Ctrl+C stops accepting requests, allows up to five seconds for active requests, then terminates and reaps the Node child.

The runner also accepts the previous version-1 manifest layout using `node_modules/next/dist/bin/next` with `["start"]`, provided the artifact actually contains that CLI and its dependencies. Rebuild older incomplete artifacts to get the new production entrypoint.

Override the ports when needed (they must be different):

~~~text
meshscale-builder run .meshscale/output --port 8080 --runtime-port 8100
~~~

For GET and HEAD, only files in the artifact's `static/` directory are served directly:

| URL | Artifact file |
| --- | --- |
| `/favicon.ico` | `static/favicon.ico` |
| `/_next/static/chunks/app.js` | `static/_next/static/chunks/app.js` |
| `/static/logo.png` | `static/static/logo.png` (from `public/static/logo.png`) |

There is no extra `/static` alias: public assets keep their original URL paths. Static responses support content types, HEAD, byte ranges and conditional requests through the filesystem service. Directory paths are not turned into index pages. Traversal and Windows path escapes are rejected.

Everything else, including `/`, `/dashboard`, `/_next/image`, missing assets and non-GET/HEAD requests, is streamed to Next.js. The proxy preserves method, path/query, body, Host, response status, redirects and multiple cookies, removes hop-by-hop headers, and sets forwarding headers from the local connection. It does not attempt to serve generated HTML routes or bypass Next.js routing for them. HTTP upgrades/WebSockets are not supported in this first local runner and return 501; proxy connection failures return 502 and are logged.

## Output efficiency

The builder excludes `.next/cache`, `.next/standalone` and build-only `.nft.json` manifests from the copied Next.js tree. It also avoids walking an already collected dependency path again and avoids re-copying traced `.next` entries during the runtime-tree copy.

This is deliberately conservative: traced dependencies (including complete traced package directories), source maps and generated HTML/data files are retained because arbitrary pruning can break runtime imports or routes. `.next/static` remains in the runtime as well as the edge-facing `static/_next/static` tree so the normal Next.js server remains functional when handling requests itself. No hard links, compression or cross-path package deduplication are introduced. Startup tracing may add dependencies missing from older, incomplete artifacts; savings depend on the application and these changes do not promise a fixed percentage reduction.

## Upload (phase E)

Upload an existing artifact independently:

~~~powershell
.\meshscale-builder.exe upload .meshscale\output --org-id org_123 --project-id project_456
~~~

The build ID comes from the artifact's manifest. Optional `--build-id build_123` asserts that it matches; it does not rename a deployment. Supplied organization/project IDs must match the manifest when already recorded. IDs contain 1-128 ASCII letters, digits, underscores or hyphens.

Object keys use the exact **organization/project/build** prefix, without a `deployments/` wrapper:

~~~text
org_123/project_456/build_123/
    _upload.json
    manifest.json
    static/favicon.ico
    static/_next/...
    runtime/.meshscale-server.cjs
    runtime/node_modules/...
~~~

### Credentials and dotenv

Create a builder `.env` using `.env.example`, or set terminal environment variables:

~~~dotenv
MESHSCALE_R2_ACCOUNT_ID=your_32_character_cloudflare_account_id
MESHSCALE_R2_ACCESS_KEY_ID=your_r2_s3_access_key_id
MESHSCALE_R2_SECRET_ACCESS_KEY=your_r2_s3_secret_access_key
MESHSCALE_R2_BUCKET=your-bucket
~~~

Use an R2 S3 API token with Object Read & Write permissions scoped to the target bucket, not a general Cloudflare API token. The uploader signs requests using AWS Signature V4, region `auto`, at `https://<account-id>.r2.cloudflarestorage.com`. The bucket must already exist.

By default the uploader searches for `.env` in the current directory and parents. `--env-file C:\path\to\r2.env` selects a specific file and fails if missing or malformed. Terminal values take precedence over file values; an explicitly empty terminal setting is an error, not a fallback. The original mixed-case `MESHScale_R2_*` spelling is accepted as an alias; canonical uppercase terminal variables take precedence when both are set.

~~~powershell
$env:MESHSCALE_R2_ACCOUNT_ID = "your-account-id"
$env:MESHSCALE_R2_ACCESS_KEY_ID = "your-access-key"
$env:MESHSCALE_R2_SECRET_ACCESS_KEY = "your-secret-key"
$env:MESHSCALE_R2_BUCKET = "your-bucket"
.\meshscale-builder.exe --env-file C:\config\r2.env upload .meshscale\output --org-id org_123 --project-id project_456
~~~

Dotenv files are ignored by Git (except the example), loaded without modifying process-global environment, and never added to artifacts. R2 settings are stripped from package-manager/build/tracing/runner child environments. The uploader rejects dotenv files found inside an artifact and does not print credential values or dotenv source lines.

### Publication, immutability and progress

Before making network writes, the uploader validates the artifact and takes a temporary on-disk snapshot so files cannot change during upload. It uploads only `manifest.json`, `static/` and `runtime/`, preserves relative paths, and rejects links, unsupported entries and unexpected top-level files.

It first creates `_upload.json` as a reservation using `If-None-Match: *`. Every other object is also create-only. Data files are streamed with up to four concurrent requests and appropriate content types; `manifest.json` is uploaded **last**, after all data requests succeed. Consumers must consider a deployment ready only when that manifest exists.

Object-key path segments are RFC 3986 percent-encoded before signing and sending, including brackets in Next.js filenames (such as `[root-of-the-server]`), plus signs and Unicode. This changes the HTTP representation, not the stored object key. R2 failures report the HTTP status, a bounded error code (for example `SignatureDoesNotMatch` or `AccessDenied`) and request ID when available. Raw response XML is not logged because signing errors can echo sensitive request details.

Progress is reported as `Upload 42.3% (123/456 files, ... bytes)` to stderr, based on bytes acknowledged by R2. It starts at 0% after reserving the prefix and reaches 100% only after the manifest upload succeeds. Large individual files advance progress when their upload is acknowledged.

Existing deployments cannot be overwritten, including by concurrent uploaders. Failures/cancellation leave the reserved prefix and any already uploaded objects intact: there is no automatic deletion, overwrite, resume or retry with the same ID. Use a fresh build ID and rebuild after a partial or uncertain upload; orphaned prefixes can be cleaned up separately. A local artifact built with `--no-upload` can be uploaded once later.

This first version uses single-object PUTs, rejects files larger than 5 GiB before reserving a prefix, and has a five-minute timeout per request. Multipart upload, content-addressed deduplication and control-plane production aliases are intentionally not implemented.

## Validation

`cargo test` covers artifact materialization, size/copy exclusions, manifest validation, static routing, proxy semantics, Node startup failures, port conflicts and child cleanup. Uploader tests use a local mock S3 endpoint to verify signing headers, exact keys/bytes, manifest-last publication, immutable conflicts, parallel uploaders, failures, progress and dotenv precedence without Cloudflare credentials. The startup-tracing and Node lifecycle tests require `node` on PATH. Use `cargo clippy --all-targets -- -D warnings` for linting.

The opt-in integration test installs and builds a real Next.js application, deletes its source checkout, then checks dynamic HTML, a generated page, saved configuration, a POST API route and a public asset through the runner:

~~~text
cargo test runtime::tests::runs_relocated_nextjs_application -- --ignored --nocapture
cargo test runtime::tests::runs_relocated_pnpm_nextjs_application -- --ignored --nocapture
~~~

These require npm, Node and network access. The pnpm test obtains pnpm 10 through `npm exec` and exercises an isolated pnpm dependency layout.

## Next.js tracing

Next.js itself uses @vercel/nft during production builds and emits `.nft.json` manifests, including `.next/next-server.js.nft.json` for the production server. The builder consumes those manifests directly. If the project enables Next's `output: "standalone"`, the generated `.next/standalone` tree is intentionally ignored: it has its own copied `.nft.json` files whose paths are relative to the standalone staging tree, not the original project root. MeshScale builds its own relocatable runtime from the source project's tracing manifests instead.

Next.js's application/server manifests are the primary source of runtime dependencies. They do not necessarily include everything needed to launch the server (for example, the `next start` CLI or programmatic startup modules). The builder additionally traces its generated production entrypoint using the NFT implementation bundled with the installed Next.js package (`next/dist/compiled/@vercel/nft`); customers do not need to declare a separate NFT dependency. Tracing errors fail the build and NFT warnings are logged.

The builder preserves the logical paths recorded by each trace while resolving the source through the filesystem. This is important for pnpm: a traced `node_modules/next/...` file may physically resolve through pnpm's `.pnpm` store links, but the output must still contain the normal `node_modules/next/...` path expected by Node.js. This materializes traced dependencies instead of copying pnpm symlink/junction layout into the artifact.

Materializing a linked package also changes Node's dependency-search ancestry. The builder therefore restores each linked package's dependency context under its own `node_modules`, using only files already included in the traces. For example, traced `@swc/helpers` files from pnpm's store are also placed under `node_modules/next/node_modules/@swc/helpers`. Transitive dependencies keep their package-specific versions rather than being globally hoisted. This can add necessary copies, but avoids artifacts that validate structurally and then fail with missing-module errors at startup.

NFT traces can also record package directories, including pnpm directory symlinks and Windows junctions such as `node_modules/@next/env`. The builder recursively materializes their contents (including empty directories and nested directory links) at the recorded logical paths. It does not skip these entries or preserve their links. Every resolved entry must remain inside the build project root; missing entries, traversal errors and link cycles fail the build explicitly.

## Platform support

The builder targets:

- Linux
- Windows

Other operating systems are intentionally unsupported.

The artifact validation rejects symbolic links and Windows junction/reparse-point links so the generated runtime can be relocated independently of the source checkout. Native dependencies still require a compatible operating system, architecture and Node version; a Windows build is not automatically deployable to Linux. The generated `.next/standalone` staging tree is also excluded because it is not part of the MeshScale runtime artifact.

## Security

The GitHub access token is currently supplied through --access-token because this is still an internal prototype interface. It should eventually be injected through a safer secret mechanism so it is not exposed in process arguments.

Build execution is not sandboxed yet. Only run builds from repositories that MeshScale is prepared to execute with the privileges of the builder host.
